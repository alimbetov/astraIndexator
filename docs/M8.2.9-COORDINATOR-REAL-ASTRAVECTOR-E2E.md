# M8.2.9 Coordinator Wiring + Real AstraVector E2E

## Status

Implementation and automated PostgreSQL qualification are owned by AstraIndexator CI.
Live AstraVector smoke is a separate operator gate because the portable deployment requires private registry/model credentials.

The canonical AccessZone reminder for this milestone is `ACCESS-ZONE-CODE-CONTRACT-FREEZE.md`. It must be read before changing producer DTOs, persistence, replay, coordinator, or AstraVector wire mapping.

## Deployment topology

AstraIndexator and AstraVector use the same PostgreSQL instance/database in portable deployment.
The canonical local deployment defaults are:

```text
POSTGRES_DB=astravector
POSTGRES_USER=astravector_app
```

AstraIndexator must still own only its own schema:

```text
astra_indexator.*
```

Shared PostgreSQL is deployment topology, not a substitute for service contracts. AstraIndexator must not read or mutate AstraVector-owned tables for ingestion/reconciliation. Runtime integration remains through `AstraVectorIngestionFacade` gRPC.

## Coordinator execution path

```text
JobCoordinator claim/lease
        ↓
producer requested_access_zone_code remains durable and unchanged
        ↓
ASTRAVECTOR_START
        ↓
StartLogicalDocumentIngestion(access_zone_code=<same four-digit string>)
        ↓ durable DeliveryCheckpoint.ingestion_session_id
ASTRAVECTOR_APPEND
        ↓
PREPARED → Append → ACCEPTED for deterministic batches
        ↓
final_content_hash persisted
        ↓
ASTRAVECTOR_FINALIZE
        ↓
Finalize + ambiguity reconciliation
        ↓ optional AstraVector internal DocumentRef identity evidence
ASTRAVECTOR_READINESS
        ↓
GetDocumentVectorStatus until configured completion boundary
        ↓
JobCoordinator.complete
```

## Crash/restart invariants

1. `requested_access_zone_code` remains the producer selector and is never replaced by an internal UUID.
2. Existing `DeliveryCheckpoint.ingestion_session_id` always wins over creating a new session.
3. If Start succeeded remotely but the worker died before local bind, the next worker reconstructs the same deterministic idempotency key and replays Start with the same persisted `accessZoneCode`.
4. Accepted batches are never sent again; PREPARED batches are replayed with the same `batchIndex + batchContentHash`.
5. Reconstructed final content must match the persisted `final_content_hash`.
6. A stale lease cannot advance stages or complete the job.
7. Completion occurs only after vector readiness reaches the configured boundary; production default requires `ACTIVE + searchable=true`.

## AccessZone code-only path

Code-only ingestion is a first-class supported path. `accessZoneCode` is a string matching `^[0-9]{4}$`, lexically `0000..9999`, and is passed unchanged to `StartLogicalDocumentIngestionRequest.access_zone_code`. AstraIndexator does not convert the code to an integer and does not derive or require a UUID before ingestion.

A direct successful Finalize currently returns `DocumentRef.access_zone_id`. AstraIndexator may persist that value separately as `DeliveryCheckpoint.resolved_access_zone_id` because the current `GetDocumentVectorStatus` wire requires `DocumentRef`. This is downstream identity evidence only; it never replaces or mutates `IndexationJob.requested_access_zone_code`.

One upstream recovery gap remains explicit: if Finalize has an ambiguous transport result and `GetLogicalDocumentIngestionStatus` later reports `COMPLETED`, that status response currently does not expose `DocumentRef`, while vector-status lookup currently requires the internal `access_zone_id`. AstraIndexator reports `FinalizeReadinessIdentityUnavailable` / `DeliveryRecoveryContractGap` rather than reading AstraVector-owned registry tables, deriving UUID from code, or creating a new version. This is a public-wire recovery gap, not an AccessZoneCode resolution requirement.

## Automated qualification

`tests/test_m8_2_9_coordinator_e2e_postgres.py` covers:

- complete claim → Start → Append → Finalize → searchable → complete flow;
- durable session reuse after restart without a second Start;
- deterministic batch checkpoints and final hash persistence;
- code-only selector preserving a leading-zero code byte-for-byte from PostgreSQL to `StartIngestionCommand`;
- downstream internal UUID evidence remaining separate from producer `requested_access_zone_code`;
- one PostgreSQL instance with AstraIndexator schema ownership.

`tests/test_access_zone_code_contract_freeze.py`, `tests/test_m8_1_boundary_normalization.py`, and `tests/test_m8_2_proto_mapper.py` additionally guard lexical format, singular/plural normalization, mismatch rejection, and protobuf preservation of leading zeroes.

## Live AstraVector smoke gate

Run this only in an environment where the portable AstraVector deployment is already healthy and credentials are available outside the repository.

Required runtime inputs:

```text
ASTRA_INDEXATOR_DATABASE_URL=<same PostgreSQL database used by AstraVector>
ASTRAVECTOR_GRPC_TARGET=127.0.0.1:50051
```

The AstraIndexator DSN should point to the same `astravector` database but migrations/tables must stay under `astra_indexator` schema.

Suggested smoke acceptance sequence:

1. Start PostgreSQL/Qdrant/AstraVector using `agent-astradeployment-portable-local-1.0/deploy/local`.
2. Apply AstraIndexator Alembic migrations against the same PostgreSQL database.
3. Enqueue one UUID-zone document and one code-only document such as `accessZoneCode="0001"`.
4. Run one coordinator worker through Start/Append/Finalize/readiness.
5. Confirm `indexation_job.requested_access_zone_code` is still exactly `"0001"`, the Start request used exactly `"0001"`, and any returned internal `resolved_access_zone_id` is stored separately.
6. Repeat with worker termination after at least one remote Append and before local continuation; reclaim the expired lease and verify same-session/same-code/same-hash replay.
7. Confirm AstraVector retrieval can see the completed document when the production readiness policy is `REQUIRE_SEARCHABLE`.

Live smoke result should be recorded separately from CI so missing private registry/Nexus credentials never produce a false green CI result.
