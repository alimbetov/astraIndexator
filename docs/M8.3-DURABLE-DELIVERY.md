## Purpose

M8.3 turns the forward-looking delivery/replay code that existed during M8.2 into a normative durable-execution contract. M8.2 remains the wire/adapter owner. M8.3 owns PostgreSQL checkpoints, idempotent execution, retry/backoff, lease fencing and crash/resume semantics.

The target invariant is:

```text
at-least-once worker execution
+
M2 lease-generation fencing
+
M7 prepared-artifact replay
+
M8.2 deterministic wire identity/hash
+
PostgreSQL durable delivery checkpoints
=
crash-safe AstraVector delivery without parser/OCR rerun
```

M8.3 does not own long-running local/downstream reconciliation or lifecycle repair; those remain M8.4/M9 concerns.

Critical TZ-13 rules:

1. processing is at-least-once, not distributed exactly-once;
2. stale workers must not advance durable delivery checkpoints;
3. recovery prefers compatible durable prepared artifacts over parser/OCR recomputation;
4. ambiguous mutating outcomes are reconciled/replayed using the same logical identity;
5. Append replay uses the same `batchIndex + batchContentHash + logical bytes`;
6. no automatic document-version bump is allowed to escape a retry/recovery conflict.

## M8.3 decomposition

### M8.3.0 — Ownership / fencing foundation

Qualify that every durable delivery mutation is made only by the current lease generation and that mutating RPC deadlines fit inside the remaining lease window.

Required evidence:

- expired/stale worker cannot create or advance delivery checkpoint state;
- stale worker cannot begin a new Start/Append/Finalize after ownership loss is known;
- Start acknowledgement cannot be bound after ownership loss during the RPC;
- stale worker cannot persist `final_content_hash` or `resolved_access_zone_id`;
- if ownership is lost during a mutating Append after remote acceptance, local ACCEPTED is not committed by the stale worker;
- reclaimed owner reuses the same persisted PREPARED batch and replays the same hash;
- a mutating RPC is not started when `remaining lease < rpc deadline + safety margin`.

Implementation is in `application/durable_append_delivery.py` and production wiring in `application/astravector_delivery_coordinator.py`.

### M8.3.1 — Retry / backoff / poison-job policy

Add stage-aware error classification and bounded retry scheduling using PostgreSQL time. Automatic retry must preserve document identity, AccessZone/TTL intent, ingestion identity and idempotency keys. Retry exhaustion transitions to durable terminal/dead-letter evidence instead of infinite re-execution.

### M8.3.2 — Crash/resume from M7 prepared artifacts

A reclaimed worker must verify the M7 manifest/checkpoint and rebuild M8.2 `LogicalBlock[]` from durable prepared artifacts. Parser/OCR/splitter are not rerun when compatibility and integrity checks pass.

### M8.3.3 — Full durable-delivery qualification

PostgreSQL/Testcontainers failure-injection matrix across at least:

```text
crash before Start bind
crash after Start remote success / before local bind
crash before Append
crash after Append remote acceptance / before local ACCEPTED
crash between batches
crash before/after Finalize boundary
lease expiry before durable mutation
lease expiry during remote mutation
retry/reclaim after worker death
```

Completion still uses the already-qualified M8.2 SEARCHABLE boundary. Long-running reconciliation over time is not redefined here.

## M8.3.0 audit finding

The M8.2 branch already contained useful `DeliveryCheckpoint`, `DeliveryBatch`, PREPARED/ACCEPTED replay and restart regression code. However, `DeliveryBatchRepository.bind_session()`, `prepare_batch()` and `mark_accepted()` were callable using only `job_id`, and `AppendDeliveryRunner` did not require a current `LeaseToken`.

That is insufficient for M8.3 because a stale worker can retain an old in-memory `job_id` after lease expiry. TZ-13 requires authoritative delivery mutations to be fenced by the current `(job_id, worker_id, lease_generation, non-expired lease)`.

M8.3.0 therefore introduces `DurableAppendLeaseFence`:

```text
SELECT indexation_job.id
WHERE id = token.job_id
  AND worker_id = token.worker_id
  AND lease_generation = token.lease_generation
  AND status = PROCESSING
  AND lease_until >= PostgreSQL now()
FOR UPDATE
```

The row lock is held in the same transaction that installs/advances the delivery checkpoint, preventing concurrent reclaim from racing that local authoritative mutation.

## Production coordinator wiring

`AstraVectorDeliveryCoordinator` now carries the `LeaseToken` through the mutating delivery path.

```text
load owned job
  -> fenced by current lease including lease_until

Start
  -> safe RPC-window check
  -> remote Start
  -> fenced transaction binds ingestion_session_id

Append
  -> DurableAppendDeliveryRunner
  -> PREPARED before network
  -> safe RPC-window check
  -> remote Append
  -> fenced ACCEPTED transaction

final_content_hash
  -> fenced checkpoint transaction

Finalize
  -> safe RPC-window check before mutating runner

resolved_access_zone_id
  -> fenced checkpoint transaction

completion
  -> existing M2 JobCoordinator fencing
```

A stale worker can therefore observe a remote acknowledgement but cannot authoritatively mutate local delivery state after its lease has expired or its generation has been superseded.

## Durable Append transaction boundaries

```text
TX-1
  assert current lease + lock job row
  bind session / PREPARED batch
COMMIT

TX-2
  assert rpc deadline fits inside current lease window
COMMIT

Append(batchIndex=N, hash=H)

TX-3
  assert current lease + lock job row
  mark same batch ACCEPTED
  advance next_batch_index
COMMIT
```

If the remote Append succeeds but ownership is lost before TX-3, TX-3 fails closed. The PREPARED evidence remains authoritative and the next owner replays the same `N + H` according to AstraVector idempotency semantics.

## RPC deadline versus lease window

A merely non-expired lease is not enough to safely begin a long mutating RPC. M8.3.0 therefore requires:

```text
remaining lease seconds >= mutating RPC deadline seconds + safety margin seconds
```

The remaining lease is calculated from PostgreSQL `now()`, not the worker wall clock. When the inequality does not hold, `LeaseRpcWindowTooShort` is raised before the network call. The delivery layer does not silently heartbeat/renew the lease; lease renewal remains an explicit coordinator/worker responsibility.

Current baseline values are:

```text
mutating RPC deadline = 30s
safety margin         = 5s
```

These are wiring defaults, not protocol constants. Deployment composition must keep the coordinator's `mutating_rpc_deadline_seconds` aligned with the actual AstraVector gRPC adapter deadline.
