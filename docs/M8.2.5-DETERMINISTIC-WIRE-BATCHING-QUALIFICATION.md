## Scope

M8.2.5 qualifies the pure planning boundary between canonical `LogicalBlock[]` and the ordered sequence of Append commands.

It proves:

1. deterministic canonical block order;
2. contiguous zero-based `batch_index` assignment;
3. exactly one final `is_last_batch=true` marker;
4. deterministic `batch_content_hash` for identical logical input;
5. local enforcement of the qualified AstraVector block-count limit;
6. local enforcement of the qualified AstraVector logical-block byte limit.

This step deliberately does **not** qualify PostgreSQL delivery checkpoints, crash/resume, retry counters, backoff timing, leases/fencing or remote acknowledgement replay. Existing M8.2.5 durable-delivery code remains regression-covered, but those durability semantics belong to M8.3 qualification.

## Pinned upstream authority

The batching limit is reviewed against the pinned AstraVector server implementation:

```text
repository:  alimbetov/llm2
server blob: 07afff94c4f3825ec953df55cd407ed7c653151a
```

AstraVector rejects Append when either condition is true:

```text
blocks.len() > chunked_ingestion_max_blocks_per_batch
sum(logical_block_size_bytes(block)) > chunked_ingestion_max_batch_bytes
```

The pinned server `logical_block_size_bytes` counts:

```text
UTF-8 bytes(block_id)
+ UTF-8 bytes(parent_block_id)
+ UTF-8 bytes(text)
+ Σ UTF-8 bytes(metadata key) + UTF-8 bytes(metadata value)
```

It does not use protobuf `ByteSize`, canonical hash JSON length, source-location bytes or source-link bytes for this admission check. AstraIndexator therefore mirrors that exact public-server admission calculation instead of inventing another byte definition.

## Deterministic planning contract

Input order is not authoritative. Before batching:

```text
blocks -> sort by (order_index, block_id)
```

Duplicate `block_id` or duplicate `order_index` is rejected because either makes replay identity/order ambiguous.

After canonical ordering, the planner fills each batch in order until adding the next block would violate either configured limit:

```text
max_blocks_per_batch
max_batch_bytes
```

The next block then starts the next batch. A single block that exceeds `max_batch_bytes` cannot be repaired by batching and is rejected locally before transport.

For a planned sequence of N batches:

```text
batch_index = 0 .. N-1
is_last_batch = false for 0 .. N-2
is_last_batch = true only for N-1
```

The batch hash remains the M8.2.1 canonical hash of the blocks in that batch. The final-content hash remains independent of batch boundaries and is computed from the canonical full-document block order.

## Configuration rule

`max_blocks_per_batch` must be positive.

`max_batch_bytes`, when configured, must be positive. `None` preserves compatibility for callers that have not yet supplied the AstraVector runtime byte limit, but production wiring must use a value aligned with the deployed AstraVector configuration before claiming bounded Append admission.

This is intentional: the server limit is runtime configuration, not a protobuf constant. AstraIndexator must not silently guess a byte ceiling and claim it matches AstraVector.

## Non-goals

M8.2.5 does not qualify:

- `DeliveryCheckpoint` durability;
- `DeliveryBatch` PREPARED/ACCEPTED recovery semantics;
- crash after remote acceptance;
- retry/backoff execution;
- lease/fencing ownership;
- Finalize/Abort reconciliation;
- restart/session reuse;
- vector readiness reconciliation.

Those durable execution concerns remain for M8.3 and later qualification boundaries.
