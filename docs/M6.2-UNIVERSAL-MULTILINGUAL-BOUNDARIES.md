# M6.2 — Universal Multilingual Boundary Layer

## Purpose

M6.2 generalizes M6 sentence/word/grapheme segmentation beyond RU/KK/EN without turning AstraIndexator into a hand-written collection of ad-hoc rules for every language.

The design follows a layered linguistic model:

1. document structure from M4/M5 remains stronger than linguistic punctuation;
2. Unicode text-boundary properties provide a deterministic cross-script baseline;
3. locale tailoring handles punctuation/abbreviation conventions that Unicode alone cannot infer;
4. ICU is an explicit production backend for locale/CLDR and dictionary-aware segmentation;
5. AstraIndexator's RAG hard guards and provenance remain above the linguistic backend.

References:

- Unicode Standard Annex #29 — Unicode Text Segmentation;
- Unicode Standard Annex #14 — Unicode Line Breaking Algorithm;
- ICU Boundary Analysis / BreakIterator;
- CLDR sentence-break suppressions.

## Philological findings

### There is no universally sufficient punctuation regex

A full stop is overloaded by abbreviations, decimals, versions, domains and identifiers. Many languages also use script-specific sentence punctuation. Plain text can remain linguistically ambiguous even with a locale hint. The implementation therefore treats sentence segmentation as a versioned policy, not as ground truth.

### Script families differ materially

#### Latin/Cyrillic alphabetic languages

Typical terminal punctuation is `. ! ? …`, but abbreviation suppression is language-specific. Existing RU/KK/EN profiles remain tailored, including mixed RU/KK/EN safety behavior.

#### Greek

ASCII semicolon `;` is conventionally used as a question mark in Greek. M6.2 enables it only for `el`, never globally.

#### CJK

Chinese and Japanese commonly use `。！？` and do not require ASCII spaces after sentence punctuation. M6.2 permits an immediate next sentence after an unambiguous Unicode sentence terminal.

Word segmentation is not inferred from spaces. Unicode fallback does not claim reliable word-based size guards for complex scripts; ICU is the recommended backend when dictionary-aware word statistics are required.

#### Arabic-script languages

Arabic question mark `؟` and other Unicode sentence-terminal punctuation are recognized through Unicode properties. No Latin transliteration or punctuation rewriting is performed.

#### Indic scripts

Danda `।` and double danda `॥`, where classified as sentence-terminal Unicode characters, are recognized without requiring Latin punctuation.

#### Armenian, Ethiopic, Myanmar and other scripts

Native Unicode sentence-terminal characters are recognized generically through Unicode `Sentence_Terminal` rather than by a growing hard-coded language switch.

#### Thai/Lao/Khmer/Myanmar and no-space writing systems

Word boundaries cannot be reconstructed reliably from whitespace. Unicode defines a deterministic baseline, but production-quality lexical segmentation may require dictionaries. ICU's BreakIterator supplies dictionary engines for supported complex scripts. M6.2 therefore distinguishes word-count value from word-guard reliability.

### Mixed-language documents

A language switch is not itself a sentence boundary. Source structure and punctuation remain authoritative. RU/KK/EN mixed abbreviation safety remains available; other locale-specific precision is obtained with the ICU backend and the element's BCP-47 `language_hint` where available.

## Backend contract

`SplitterProfile.sentence_boundary_backend` is explicit and is included in the splitter profile configuration hash and fragment identity.

### `unicode`

Default portable backend:

- Unicode `Sentence_Terminal` property;
- locale-specific Greek `;` tailoring;
- RU/KK/EN abbreviation protections;
- terminal-capable abbreviation look-ahead;
- unambiguous terminal punctuation may break without following ASCII whitespace;
- blank-line paragraph boundary;
- Unicode word-boundary approximation;
- complex-script word counts are marked unreliable for RAG word guards;
- extended grapheme clusters protect forced splitting.

### `icu`

Optional production backend (`pip install .[linguistics]` plus a compatible system ICU runtime):

- ICU sentence BreakIterator;
- locale selection from BCP-47 language hint;
- CLDR/ICU sentence suppressions via `ss=standard` where available;
- ICU word BreakIterator;
- dictionary-aware segmentation for supported no-space scripts.

If `icu` is configured but PyICU is unavailable, the worker fails explicitly with `SPLITTER_ICU_UNAVAILABLE`; it never silently changes segmentation backend.

## Grapheme safety

Forced character splitting operates on Unicode extended grapheme clusters (`\X`) instead of Python code-point slicing. This protects:

- base + combining mark sequences;
- emoji ZWJ families;
- many conjunct/combined visible characters.

If a single grapheme cluster itself exceeds the configured hard character limit, M6 fails with `SPLITTER_GRAPHEME_EXCEEDS_HARD_CHAR_GUARD` rather than corrupting the text.

## Word-count reliability

Each internal logical unit carries both:

- `word_count`;
- `word_guard_reliable`.

For portable Unicode segmentation, complex dictionary-dependent scripts set `word_guard_reliable=false`. In that case:

- character guards remain authoritative;
- sentence guards remain authoritative;
- word target/soft/hard thresholds do not force a misleading split;
- the fragment exposes `metadata.wordCountReliable=false`.

With ICU, dictionary-aware word segmentation is treated as reliable for the configured locale/backend.

## RAG invariants

M6.2 does not change the core M6 rules:

- structure-first before language fallback;
- no blind sliding overlap;
- no embedding/tokenizer dependency inside AstraIndexator;
- original provenance is never expanded by synthetic context;
- hard char/sentence guards always hold;
- hard word guard holds whenever word segmentation is declared reliable;
- backend/profile identity participates in deterministic fragment identity.

## Verification corpus categories

The minimum multilingual matrix covers:

- RU / KK / EN and mixed technical text;
- Chinese;
- Japanese;
- Arabic;
- Hindi/Indic danda;
- Armenian;
- Myanmar;
- Ethiopic;
- Greek question-semicolon;
- blank-line paragraph boundaries;
- version/domain/IP-like period overloads;
- combining marks;
- emoji ZWJ grapheme clusters;
- no-space-script word reliability.

## Remaining calibration

No implementation can truthfully claim perfect linguistic segmentation for every sentence in every language from plain text alone. M6.2 therefore defines correctness as:

1. standards-based Unicode baseline;
2. explicit locale-aware backend;
3. deterministic, versioned behavior;
4. no destructive normalization;
5. measurable corpus quality.

TZ-17 must maintain representative multilingual corpora and measure boundary precision/recall for actual deployment languages. New language-specific tailoring is accepted only with corpus evidence and a versioned rule/backend change.
